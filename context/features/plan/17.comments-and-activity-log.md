# 17. Comments and activity log

## Why

- A team tool without discussion and history is not credible: who moved the task, who changed the due date, why
- Interview angle: "Audit trail in the database: triggers vs application code?", "Why can the client not forge history?"

## Scope

1. ADR: activity written only by database triggers (`security definer`, `set search_path = ''`), never by the client
2. Migration: `task_comments(id, task_id, workspace_id, author_id, body, created_at, edited_at)` — members read, the author edits and deletes, plain text only (no HTML; length limit); `task_activity(id, task_id, workspace_id, actor_id, kind, payload jsonb, created_at)` — insert only by triggers on `tasks`, `subtasks`, `task_contacts`, `task_labels`, `task_files`; no insert/update/delete policy for clients
3. Activity kinds: created, moved (from → to), renamed, due date changed, priority changed, assignee added/removed, label added/removed, file added/removed, subtask done/undone, comment added
4. Task detail: a timeline of comments and activity (newest first, paged), comment box (kit textarea, Signal Forms), edit/delete own comment with confirm
5. Rendering of activity text through the message map (i18n keys in 22); dates relative and absolute (`CLOCK`)
6. Integration tests: a member cannot insert activity directly; a non-member sees no comments; editing someone else's comment is refused; each trigger writes the expected entry

## Acceptance criteria

- Every change of a task leaves an activity entry the client could not have forged; comments work end to end (E2E)
