# 9. Auth completeness and account settings

## Why

- No `onAuthStateChange` listener: an expired session, a token refresh or a sign-out in another tab is not reflected; stores keep the previous user's data after sign-out
- No email confirmation, no password reset, no way to delete your own account (GDPR Art. 17)
- Interview angle: "How does session handling work in an SPA?", "Where do you store tokens?", "What does a guard protect and what not?"

## Scope

1. `AuthStore` listens to `onAuthStateChange` once (`SIGNED_IN`, `SIGNED_OUT`, `TOKEN_REFRESHED`, `USER_UPDATED`, `PASSWORD_RECOVERY`); sign-out in any tab → `currentUserId()` becomes `null`, so every store keyed by it empties itself (ADR of 6, no reset calls), navigate to login
2. Email confirmation on sign-up (local stack: Inbucket/Mailpit; hosted: Supabase email for now, custom SMTP in `todo-before-live.md`), a "check your inbox" page, resend
3. Password reset: request page, the recovery link route, set new password
4. **Account settings page**: name (contact initials and color follow), avatar color, preferred language (stored for 22), change password, MFA with TOTP, opt-in per user, not enforced (a member's account guards other people's data; verify the plan limits in the Supabase docs), delete account (step 6)
5. Convert the anonymous demo to a real account (link email + password to the anonymous user) keeping its data
6. Delete own account: confirm dialog with password re-entry, the `delete-user` Edge Function (from 3, the only operation that needs the service role) called with `supabase.functions.invoke` (the client sends the JWT) deletes the caller, the workspace is handed over or deleted per the ADR of 8; sign out
7. Guards: `authGuard` also waits for the initial session; deep link after login returns to the requested URL

## Acceptance criteria

- Sign-out in tab A signs out tab B; reset and confirmation work end to end on the local stack (E2E with the local mail catcher)
- Account deletion removes the user's personal data (integration test)
