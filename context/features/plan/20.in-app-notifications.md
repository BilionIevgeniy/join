# 20. In-app notifications

## Why

- Members miss that a task was assigned to them or is due tomorrow
- Interview angle: "Scheduled jobs in Postgres (`pg_cron`)", "Pushing events to the client"

## Scope

1. Migration: `notifications(id, user_id, workspace_id, kind, task_id, payload, read_at, created_at)`; RLS: a user reads and marks only their own
2. Producers: a trigger on `task_contacts` insert ("assigned to you"); a daily `pg_cron` job for "due tomorrow" and "overdue" (idempotent: one per task and day)
3. Delivery: Realtime on the user's own notifications (19); a bell in the header with an unread count, a list (kit menu/panel), mark as read / all read, link to the task (routed dialog from 11)
4. Settings: turn kinds on or off per user (account settings from 8)
5. Retention: read notifications deleted after a fixed period (job)
6. Integration tests: a user never sees another user's notifications; the job does not create duplicates

## Non-goals

Email and push notifications (need SMTP / a push service: `context/todo-before-live.md`).

## Acceptance criteria

- Assigning a member shows them a notification within a second; the daily job produces due reminders exactly once
