# 9. Files in Storage and subtasks as rows

## Why

- Attachments are Base64 strings inside the task's jsonb column (a course requirement that no longer applies): every task load downloads every image, rows grow by a third over the file size, there is no caching and no access control per file
- Subtasks are one jsonb array per task: two people toggling different subtasks both rewrite the whole array and one toggle is lost (daily with realtime in 19); no activity entry per subtask is possible
- Interview angle: "How do you handle file uploads securely?", "Signed URLs?", "How do you migrate data without downtime (expand → migrate → contract)?", "jsonb or a table?"

## Scope

1. ADR: files in a private Storage bucket, metadata in a table; subtasks as rows
2. Migration: private bucket `task-files` with size limit and allowed MIME types (images; decide PDF in the plan); table `task_files(id, task_id, workspace_id, path, name, mime_type, size, created_at)`; Storage policies on `storage.objects` by path `<workspace_id>/<task_id>/<file_id>` and membership
3. Upload flow: client-side checks (type, size) and compression kept (`image.utils`), upload with progress, then metadata row; failure cleans up the object
4. Display: signed URLs with short expiry, thumbnails via image transformations if the plan allows it, else client-side; the image viewer loads lazily (18)
5. Delete: removing a file or a task removes the objects (RPC or Edge Function; no orphaned objects)
6. Data migration: a one-off script (or Edge Function) moves existing Base64 files to Storage and fills `task_files`; then a later migration drops the `files` column (expand → migrate → contract, two deploys)
7. **Subtasks as rows**: table `subtasks(id, task_id, workspace_id, title, is_done, position, created_at)` with RLS on membership; toggling and editing are single-row writes (optimistic in the store); the task RPCs write subtasks in the same transaction; data migrated from the jsonb array, the column dropped in a later migration (same expand → migrate → contract)
8. Integration tests: member can read, non-member cannot (by path), `anon` cannot; size/MIME limits enforced by the bucket; subtasks of another workspace are invisible; two concurrent toggles both persist

## Acceptance criteria

- No Base64 and no subtask jsonb in the database; a non-member cannot fetch a file even with the path; E2E: attach, view, download, delete; toggle subtasks
