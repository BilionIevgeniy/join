# 3. Supabase as code and security lockdown

## Why

- The schema, RPCs, policies and the `delete-user` Edge Function exist only in the Supabase dashboard: not reviewable, not reproducible, not testable
- The live app is very likely open to anyone with the URL (to confirm with the pulled schema first):
  - the guest (`signInAsGuest`) has no Supabase session, yet reads and writes tasks and contacts → the tables must accept `anon`, and the publishable key is public
  - `upsertFromAuth` upserts `contacts` on conflict by `email`: signing up with the email of an existing contact takes over that row's `auth_user_id`
  - `deleteContact` invokes `delete-user` with any `auth_user_id`: unless the function checks the caller, any user can delete any account
- Interview angle: "How do you secure an app whose browser talks to the database?", "What is RLS?", "How do you version a database schema?"

## Scope (one commit each)

1. **Pull**: Supabase CLI as a dev dependency, `supabase init`, `supabase link` to the existing project, `supabase db pull` → the first migration; `supabase/functions/delete-user` from the deployed function; write down in the PR what the pulled policies allow (the findings above confirmed or not)
2. **Local stack**: `supabase start` (Docker), `seed.sql` with test users and data; scripts `db:start`, `db:stop`, `db:reset`, `db:types`; `.env.example`; dev environment pointing at the local stack
3. **Typed client**: `supabase gen types` → `src/app/core/supabase/database.types.ts`; `createClient<Database>`; the Supabase client provided through an `InjectionToken` (replaces `SupabaseService.db`)
4. **Profiles instead of the email upsert**: a `security definer` trigger on `auth.users` insert creates the user's `contacts` row from validated metadata (`first_name`, `last_name` passed in `signUp` options), color and initials generated in SQL or passed and validated; remove `upsertFromAuth`
5. **Demo via anonymous sign-in**: enable anonymous sign-ins; "Guest log in" calls `signInAnonymously()`; remove the fake `GUEST_USER` and the `sessionStorage` flag; enable CAPTCHA/rate limit settings as the docs recommend for anonymous sign-ins (document what was set)
6. **Lockdown migration**: RLS enabled on every table; no grants or policies for `anon` on user data; policies for `authenticated` (including anonymous users) — data stays shared among signed-in users until feature 7 scopes it by workspace (say so in the PR and the README); RPCs `security invoker`; `subtasks`/`files` columns `not null default '[]'`
7. **`delete-user`**: verify the JWT, delete only the caller's own account (an owner deleting someone else's account is not a feature); the app's "delete contact" no longer deletes auth users — only a contact without an account can be deleted by others; deleting your own account moves to feature 8
8. **Migrations to the cloud**: a `dev` and a `prod` Supabase project; CI applies migrations to `dev` on merge (or on PR for previews, decide in the plan) and to `prod` on merge to `main` with `supabase db push`, secrets from GitHub (`SUPABASE_ACCESS_TOKEN`, project refs, DB password) — never from the client
9. **Integration tests**: `npm run test:integration` (Vitest config against the local stack): `anon` reads nothing; an anonymous user and a registered user can do what the policies allow; `delete-user` refuses another user's id; the trigger creates the contact; CI job `integration` with `supabase start`
10. **`.mcp.json`**: add the Supabase MCP server for the local stack (and read-only for the dev project), after checking the current setup in the Supabase MCP docs

## Non-goals

Workspaces (7), Storage (9), password reset and email confirmation (8), moving Angular code into feature folders (5) beyond what the steps need.

## Acceptance criteria

- `supabase db reset` rebuilds the full schema locally; a new hosted project can be created from the repo
- No table is readable or writable with only the publishable key and no session (proven by a test)
- The demo button creates an anonymous session; sign-up creates the contact through the trigger
- `integration` is a required check

## Tests

The integration tests of step 9; the existing E2E does not exist yet (4).
