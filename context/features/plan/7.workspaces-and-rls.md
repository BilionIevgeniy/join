# 7. Workspaces, invitations and RLS

## Why

- After feature 3 every signed-in user still sees every task and contact: RLS can only say "all authenticated users", which is the current bug, not a tenancy model
- Interview angle: "How do you build multi-tenancy with RLS?", "How do you test that tenant A cannot see tenant B?", GDPR: no one is added to a team without consent

## Scope

1. ADR: workspaces and invitations (alternatives: one global board, per-user boards, Supabase organisations-style model)
2. Migration: `workspaces`, `workspace_members(role: owner|member)`, `workspace_invitations(email, status, invited_by, expires_at)`; `workspace_id` on `contacts`, `tasks`, `task_contacts`; existing rows moved to one legacy workspace; indexes on `workspace_id`
3. On sign-up (trigger from 3) a personal workspace with the user as owner; the anonymous demo gets a seeded demo workspace (copy of a template, cleaned up by a scheduled job or documented manual cleanup)
4. RLS on membership through a `security definer` helper (`is_member(workspace_id)`, `set search_path = ''`, not executable by `anon`); owner-only policies for members and invitations
5. RPCs: `invite_member(workspace_id, email)` (owner only; **same response whether the email has an account or not**), `accept_invitation(id)`, `decline_invitation(id)`, `leave_workspace(id)`, `remove_member(workspace_id, user_id)`; task RPCs take and check `workspace_id`
6. **Permissions**: `permissionsFor(role)` in `workspaces/domain` returns a typed set (`canInvite`, `canRemoveMember`, `canDeleteWorkspace`…); the workspace store exposes `canX` computed signals; an `ownerGuard` for owner pages; the role is read from the `workspace_members` row (not from JWT custom claims, which stay stale until the token refreshes); an integration test proves that RLS denies exactly what the matrix denies
7. **Lost updates**: `tasks.version int` (incremented by the update RPC); `update_task_with_contacts` takes `expected_version` and raises a mapped `conflict` error when it differs; the edit dialog keeps the user's input and offers "reload" (the realtime notice in 19 builds on this)
8. App: `workspaces` feature (store with the current workspace, kept in the URL or local storage), invitation inbox after sign-in, members page for owners (invite, remove), leave; all stores keyed by `currentWorkspaceId()` (ADR of 5); a simple switcher only if a user is in more than one workspace
9. Integration tests: user B gets nothing of workspace A by id (select, update, delete, RPCs); an invitee sees nothing before accepting; a removed member loses access; `anon` gets nothing; a stale `expected_version` is refused

## Non-goals

Email delivery of invitations (the invitee sees them in the app), roles beyond owner/member, billing.

## Acceptance criteria

- Cross-workspace isolation proven by integration tests in CI; E2E: invite → accept → shared board
- `security-auditor` full audit after the merge, findings fixed
