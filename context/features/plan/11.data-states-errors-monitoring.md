# 11. Data states, errors and monitoring

## Why

- Lists show nothing while loading and nothing on error (only a toast); there is no global `ErrorHandler`; errors are only `console.error`; nobody learns about errors in production
- Interview angle: "How do you handle loading and error states with signals?", "Global error handling in Angular?", "Monitoring a frontend in production, GDPR-friendly?"

## Scope

1. Every store load exposes `isLoading`, `error` and `reload()` from its `resource()`; pages show skeletons (same size as content), empty states and error states with Retry
2. Typed error model: repositories map Supabase/PostgREST/Storage errors to `{ code, message }`; one message map per feature (i18n keys in 16)
3. Global `ErrorHandler` in `core/error/` and a `Logger` service (levels, no `console.*` elsewhere — lint rule)
4. Sentry for Angular, EU region: `@sentry/angular` with the ErrorHandler integration, release and environment, source maps uploaded in CI (not deployed), PII scrubbing (no emails, no task text), sample rates; ADR with the GDPR reasoning (data processing agreement, what leaves the browser); disabled locally
5. Offline/slow network: a banner when offline; requests that fail because of the network say so

## Acceptance criteria

- Killing the local Supabase shows error states with Retry, not a blank page; a thrown error reaches Sentry (dev project) with a readable stack trace
