# 12. CDK drag and drop and accessibility

## Why

- Native HTML5 drag and drop does not work on touch; clickable `<div>`s and custom dropdowns lack keyboard handling; the modal has no focus trap; the BFSG (in force since 2025-06-28) makes WCAG 2.1 AA the expectation in Germany
- Interview angle: "How do you make drag and drop accessible?", "What is BFSG?", "How do you test accessibility?"

## Scope

1. `@angular/cdk/drag-drop`: connected lists for the columns (`cdkDropListGroup`, `cdkDropList`, `cdkDrag`), preview and placeholder styles, reordering inside a column only if the plan adds a `position` column (decide), the store's `moveTask` stays the single write
2. Keyboard alternative: the "move to" menu on every card, a proper menu (Angular Aria or CDK menu — verify which fits)
3. Dialogs via CDK Dialog (focus trap, Esc, return focus, `aria-modal`, labelled); replaces the custom `ModalService` internals or wraps them (decide in the plan)
4. Dropdowns (category, assignees) as accessible listbox/combobox (Angular Aria if it fits)
5. Live region for toasts; visible focus styles; contrast check of the theme tokens
6. axe checks: `@axe-core/playwright` in the E2E journeys (no violations of level A/AA), plus the template lint rules from 2
7. Accessibility statement page (Barrierefreiheitserklärung) in `legal`, with the known limitations and a contact

## Acceptance criteria

- The whole app works with keyboard only; drag and drop works on a phone; axe reports no A/AA violations on the main pages
